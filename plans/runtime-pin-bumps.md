# Keeping the bundled Claude Code and Codex current

Frizz provisions its own Claude Code and its own Codex — one pin per backend, declared in [`packages/server/src/runtimes.ts`](../packages/server/src/runtimes.ts) and fetched from the vendor's own npm package on first boot. The design is in [provisioned-runtimes.md](provisioned-runtimes.md); this file is the operational half: how the pins are watched, what moving one costs, and what has to be re-proven afterwards.

**A stale pin is a broken worker, not a cautious one.** Both vendors enforce minimums server-side, so lag shows up as a hard failure rather than as missing polish. The first provisioned Claude Code refused the default model outright — `400 Claude Code 2.1.207 does not support this model; version 2.1.251 or newer is required` — and the 0.146 Codex pin could never offer `gpt-6-astra`, because the catalogue server omits a model from any client below its `minimal_client_version`. Both vendors ship every couple of days, so the pins need a standing watch rather than a bump when someone notices.

## Claude Code floats past its pin (since 2026-11-09)

A server no longer waits for a release to run a newer Claude Code. The maintainer chose this on 2026-11-09, after Fable 5.2 reached users only through a pin bump, a release, npm's review and a click on Update. [`claude-float.ts`](../packages/server/src/claude-float.ts) checks npm an hour apart (the first a minute after boot) and moves the server to the newest `@anthropic-ai/claude-code-<platform>` on the bundled build's `major.minor` line. The new build is adopted only after it reports its version and the bundled SDK has opened a session on it and read its models. New threads, resumes, the model picker and the quota read then use it, and running daemons keep the build they were forked on. The adopted build is recorded in `<runtimes>/claude-float.json`, so a restart boots straight onto it.

| Case | What happens |
| --- | --- |
| npm's `latest` is a later 2.1.x | The server moves to it within the hour. |
| `latest` moves back (a pulled release) | The server follows it down, never below the bundled build. |
| `latest` is a new line (2.2.0) | The server stays on the newest 2.1.x; 2.2 waits for a release that bundles it. |
| The new build fails verification | The server stays where it is and tries that build again a day later. |
| `FRIZZ_CLAUDE_FLOAT=0`, an explicit executable, `FRIZZ_RUNTIMES=path`, or a deferred runtime | The bundled build, as before. |

**The pin is still bumped, now as the floor.** It is what a new install runs for its first minute, what an offline machine runs, and the SDK every newer build is driven by. An SDK 17 releases behind (0.3.304) drove 2.1.321 through a model list and a Bash turn on 2026-11-09, but that gap only grows, so keep it current. The log-format gate below tests the newest build on the line that has written a session here, which is the build new threads run. `scripts/verify-claude-float.mjs` drives a real stack through a move, a worker on each side of it, and a restart.

## The daily check

```
nub scripts/check-runtime-pins.mjs          # a verdict
nub scripts/check-runtime-pins.mjs --json   # the same thing for a script
```

It reads the pins from `runtimes.ts` itself, asks the registry what each vendor has published, and answers the only question that matters: **may this pin move today?** Exit `0` both current · `10` at least one behind · `1` the check itself failed.

Three things have to hold before a bump is ready, and the script reports each:

- **Behind.** The vendor has published something newer.
- **NOT "past the age floor" — bump the newest, the day it ships.** `nub` refuses any version under 24 hours old (`minimumReleaseAge=1440`, its own default), and this procedure used to treat that as a gate. It does not converge: Anthropic shipped 0.3.263 through 0.3.267 in two days, so every candidate was superseded before it aged in, and the pin was not a day behind but permanently behind (maintainer, 2026-09-09: *"I think we should ship these things as quickly as possible"*). The floor also bought no safety this procedure does not already provide — every move is verified against the real binary, which is a stronger check on a first-party runtime than waiting to see whether anyone else complains. So the Claude install passes `--minimum-release-age-exclude "@anthropic-ai/*"`, the gate stays on for the rest of the tree, and Codex was never gated at all because Frizz's own provisioner fetches it rather than the package manager.
- **Every platform tarball published.** Provisioning fetches a per-platform package, and the version tag and the platform tarballs do not land at the same instant. Bumping to a version whose tarball is missing breaks every machine that boots before it appears.

The check follows each package's npm `latest` tag. Both Anthropic packages publish to `next` first and promote to `latest` later, sometimes never: 2.1.315 only ever sat on `next`, and the next `latest` was 2.1.316. A version on `next` alone is not a bump yet.

## Who runs it, and a whole bump in order

**The releaser thread owns the pins** (maintainer 2026-11-04, retiring the standing thread that had run this watch daily since 2026-09). Run the check every day and before every release; a pin that is behind is bumped and landed on `main` first, then shipped by the sequence at the end of this file. The scripts named below live in [`scripts/pin-bump/`](../scripts/pin-bump/); each runs against the checkout it sits in, so from a bump worktree it exercises the worktree's code and pin, and each header says what it prints and what to look for. Run them as `env -u NODE_COMPAT nub …` inside a Frizz worker, which inherits `NODE_COMPAT=1` and otherwise strips TypeScript the old way.

**A Claude bump, from `scripts/check-runtime-pins.mjs` saying it is behind:**

1. **Probe the pin you are leaving, from `main`:** `nub scripts/pin-bump/claude-probe.mjs`. Two sessions through Frizz's own SDK path in a worker's environment; keep the two transcript paths it prints, and the plugin list.
2. **Branch:** `git worktree add .frizz/worktrees/pin-claude-<cli> -b pin-claude-<cli>`, then the three edits and the pnpm install in [Moving the Claude pin](#moving-the-claude-pin), which also installs the worktree. Read the lockfile diff and name any transitive sweep in the commit (react-scan depends on `react-doctor@latest`, so every lockfile write moves react-doctor and its oxlint plugin).
3. **Read what the vendor says changed.** Diff `sdk.d.ts` and `sdk-tools.d.ts` under `packages/claude-agent-sdk-runtime/node_modules/@anthropic-ai/claude-agent-sdk/` between `main` and the worktree, and read the [Claude Code changelog](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md) for EVERY version since the old pin, skipped ones included. Look for transcript records, permission and hook behaviour, SDK-session behaviour, the usage-limit line (`usage-limit.ts` classifies its text; 2.1.312 renamed "session limit" to "5-hour limit"), and anything new that is on by default. A new SDK `system` subtype reaches Frizz as `kind: "other"` (`mapSdkMessage` in `claude-agent-sdk.ts`), so it is harmless unless something should read it. When a changelog line is ambiguous, the binary settles it: its JavaScript is plain text, so searching the provisioned `claude` file for a string from the line finds the code (2.1.314's idle compaction turned out to be armed only for interactive and named entrypoints, never `sdk-ts`).
4. **Probe the new pin, from the worktree:** `nub scripts/pin-bump/claude-probe.mjs` (it provisions the build first; `provision.mjs claude` does that alone).
5. **Compare the two probes.** `nub scripts/pin-bump/tools-diff.mjs <old> <new>` for what the model is offered, `transcript-shape.mjs --old <old…> --new <new…>` for record kinds and keys, and `record-inert.mjs <kind> <new…>` for every new kind. An inert kind gets a test beside the 2.1.300 and 2.1.317 ones in `tailer.test.ts` and `transcript.test.ts`; a kind that moves the fold or the read is a parser change. Read the two plugin lists side by side: 2.1.317 added `cc-plugin-privacy`, which asks permission before a shell or web call carrying the signed-in account's email, and the worker's own PermissionRequest hook approves that ask (the probe sets `FRIZZ_THREAD` so the hook is live, as in a worker).
6. **Switch off whatever contradicts the worker contract** ([`workerPrompt.ts`](../packages/server/src/workerPrompt.ts)) in `CLAUDE_WORKER_ENV` in [`backend/types.ts`](../packages/server/src/backend/types.ts), and re-probe to prove it took; if there is no switch, report it. 2.1.302 turned fork sub-agents on for SDK sessions, which is why `CLAUDE_CODE_FORK_SUBAGENT=0` is there.
7. **Let the new transcripts sit ten minutes, then run the log-format gate** ([below](#then-re-prove-the-log-format--this-is-the-step-that-gets-skipped)). It must say `pass`, not `skipped`. It looks only at the 60 newest transcripts on the machine, so on a busy day the probe can fall out of the window: probe again and run the gate right after the ten minutes.
8. **Typecheck and the full suite in the worktree** (`nub run typecheck`, `nub run test`). Before blaming the pin for a red test, run that file on `main`: `tailer: the real shell probe is async` waits a fixed 2s for a real `lsof`, which takes about 1s on a machine running 9,000 processes; the real-launcher tests in `launcher.test.ts` and `server-owner.test.ts` time out when other threads have the load average near 400 (2.1.318's run) and pass alone; the `dev-supervisor` child-update tests fail above load 120 on any commit, so compare against the last release's commit before reading anything into them; `a served name renews its lease` has a 50ms settle window and passes alone; and a set of question tests once failed on every checkout because their fixtures were dated.
9. **Land it.** Commit (a signed commit waits for an unlocked screen; never route around a refused signature), merge `main` into the branch if it moved, `git merge --ff-only` it from the shared checkout, sync that checkout with `nub install --frozen-lockfile --minimum-release-age-exclude "@anthropic-ai/*"`, and remove the worktree and branch.

**A Codex bump** is the audit in [Moving the Codex pin](#moving-the-codex-pin), on a `codex-<version>` branch. It needs a signed-in Codex (`test -e ~/.codex/auth.json`): the catalogue comes from a real `codex exec` turn on the pin, run with the binary `provision.mjs codex` prints. Never sign in on the maintainer's behalf; without it the branch waits, and the handoff says so. Read the release notes too (`gh release view rust-v<version> -R openai/codex`) and the PRs they list, above all any that add fields to item types Frizz parses strictly: Codex 0.166 added `startedAtMs`/`completedAtMs` to every item, and the strict `fileChange` schema would have denied every file approval had the bump not caught it.

## Moving the Claude pin

The SDK version is the pin; the Claude Code build is whatever that SDK names in its own manifest. Neither is chooseable alone.

1. `packages/claude-agent-sdk-runtime/package.json` — the `@anthropic-ai/claude-agent-sdk` dependency.
2. `runtimes.ts` — `CLAUDE_AGENT_SDK_VERSION`, then `CLAUDE_CODE_VERSION` to the SDK's own `claudeCodeVersion`. Never guess the second: `runtimes.test.ts` reads it out of the installed SDK's manifest and fails on a mismatch.
3. Update the lockfile with **pnpm, not `nub install`** — `CI=true nubx -y pnpm@10 install --no-frozen-lockfile`. **Then READ THE DIFF, because pnpm is the safer tool and not a safe one.** Editing the manifest bypasses pnpm's prefer-frozen path, so it re-resolves the whole graph at `resolution-mode=highest` and every TRANSITIVE range that now admits something newer moves with your pin. Measured on 0.3.270 (2026-09-12): 210 lines rather than the usual 74, carrying oxc-parser 0.146.0 -> 0.148.0, oxlint 1.79.0 -> 1.81.0 and react-doctor 0.9.13 -> 0.9.14 — none of them declared in any manifest, all of them transitive under `packages/web`. The sweep cannot be split from the pin (with the manifest unedited pnpm goes headless and moves nothing), so the rule is to NAME it in the commit rather than to pretend it did not happen, and to rebuild the server package as the workflow does before believing the artifact is unaffected. Expect ~74 lines on a quiet day; anything larger is a finding to report, not noise to wave through. Both flags are load-bearing: `CI=true` lets pnpm purge a `node_modules` that nub built without a TTY to confirm on, and it ALSO flips pnpm's default to frozen, so without `--no-frozen-lockfile` the install refuses with "specifiers in the lockfile don't match" the moment the manifest has moved (hit on 0.3.268). Both tools leave a working tree; only one leaves a reviewable diff. `nub install` re-resolves every caret range in the workspace to its newest satisfying version, so this one-line pin arrived as a **2984-line** lockfile that also carried puppeteer 25.3.0 → 25.10.0, `@parcel/watcher`, `ws` and `@types/node` (measured 2026-09-09). pnpm reuses the existing resolutions and moves only what the manifest changed: **326 lines**, all of them the SDK and its eight platform packages. A runtime pin release must not smuggle a dependency sweep past its own review. If you do reach for nub here, it needs `--minimum-release-age-exclude "@anthropic-ai/*"` to install an SDK published today; pnpm has no age floor configured in this repo. Either way the runtime package's own `node_modules` has to end up on the new SDK, because that manifest is what the test reads.

## Moving the Codex pin

The Codex coordinate is an AUDITED one and lives in [`codex-app-server.ts`](../packages/server/src/backend/codex-app-server.ts), not in `runtimes.ts`, which imports it. A bump is a re-audit:

1. Take the release's immutable source coordinates. The tag is `rust-v<version>`; dereference the annotated tag to its commit rather than recording the tag object's own sha — `gh api repos/openai/codex/git/ref/tags/rust-v<version> --jq .object.sha`, then `gh api repos/openai/codex/git/tags/<that sha> --jq .object.sha`. Checked against the recorded `rust-v0.153.2` → `657a993c`, which is what that two-step yields.
2. Update `CODEX_APP_SERVER_SUPPORTED_VERSION` and all three fields of `CODEX_APP_SERVER_PROTOCOL_REVISION`, plus the version literal in `runtimes.test.ts`'s coordinates (and the hand-typed triple in `codex-app-server.test.ts`, and the Windows path in `codex-executable.test.ts`). Then re-read the degraded model catalogue: run the new binary once (a `codex exec` turn writes `~/.codex/models_cache.json` stamped with its `client_version`; copy it at once, because every Codex install on the machine rewrites that one file), parse it with `parseCodexModelsCache` (`nub scripts/pin-bump/codex-catalogue.mjs <copy>` does this and compares), bring `CODEX_MODELS_FALLBACK` in [`packages/shared/src/index.ts`](../packages/shared/src/index.ts) in step with it, and move `CODEX_MODELS_FALLBACK_VERSION` to the pin. `codex-models.test.ts` fails until that version matches. The same `codex exec` turn leaves a rollout in `~/.codex/sessions/`; `nub scripts/pin-bump/codex-fold.mjs <rollout>` shows what Frizz parses from each of its records.
3. Provision the new binary and run the wire-contract gate against it unskipped — `nub run test packages/server/src/backend/codex-protocol-conformance.test.ts`. It asks the binary for its own generated schema and checks both directions: every param Frizz sends still exists, and nothing the binary declares it can send is refused by a schema Frizz reads it with. The read side walks `CODEX_READS` (the schemas the bridge's handlers parse with, most of them `.strict()`) against `ServerRequest.json`, `ServerNotification.json` and `ThreadItem`, and fails on a key, a union variant or an enum value on one side only. A refusal that is meant, such as a question kind Frizz does not draw, is listed by name in `REFUSED_ON_PURPOSE` in that test, with the reason. When it fails on a new key, name the key in the schema in `codex-app-server.ts` (optional, so the previous build still parses) and decide whether Frizz should read it. It SKIPS when the installed codex is not the pin, and a skip is not a pass.
4. **Diff the schema in both directions of the wire.** The gate above judges the messages Frizz already sends and reads. It cannot see a method Frizz does not read yet and should, or one whose meaning moved under the same shape, and until 2026-11-10 it read `ClientRequest` alone, which would have passed a break shaped like 0.153's. [`scripts/pin-bump/codex-schema-diff.mjs`](../scripts/pin-bump/codex-schema-diff.mjs) compares each file's variant method set and per-variant field keys, and every definition, between two generated schema directories (its header has the command that generates them). Run it OLD NEW, then NEW OLD, then with `--control` to prove it can still see a removal. Treat a REMOVED method or field as the finding; additions are ordinarily harmless, and a new field on a schema Frizz parses `.strict()` now fails step 3 by name. On 0.153.4 → 0.154.0 all three were byte-for-byte identical in shape (81, 11 and 1 variants, nothing added or removed), while `ClientRequest` went 155 → 159.
5. **Run the app-server path live.** A schema says what the binary accepts, not what it does with it, and `codex exec` never touches the app-server a worker runs on. `env -u NODE_COMPAT nub packages/server/src/backend/_live_codex_config_sync.mts` (then again with `--control`) drives the real bridge over the production transport and proves `thread/resume` still applies Frizz's config bag; `_live_codex_shell_identity.mts` re-reads what a worker's shell can reach under each sandbox. Both use a local mock model, so they need no sign-in and spend nothing, and both pick up the provisioned pin. On 0.163.0 (2026-10-17) both passed unchanged.
6. **Decide the floor, and leave it where it is unless this bump needs it raised.** `CODEX_APP_SERVER_MINIMUM_VERSION`, beside the pin, is the oldest app-server a bridge keeps talking to. After Update & Restart the app-server that was already running is still on the PREVIOUS pin, and every Codex turn, sub-agent and background command in the project lives inside it. With the floor below the new pin that app-server keeps running and is replaced by one on the pin once the project is idle. With the floor raised to the new pin it is stopped on the first connect and all of that is cut, which is what every bump did until 2026-11-10. So raise the floor to the new pin only when this bump makes the bridge SEND or DEPEND ON something the previous build lacks:
   - a request, or a request parameter, the bridge now sends that step 4's `OLD NEW` diff lists as added;
   - a notification or response field `codex-app-server.ts` now needs in order to work, as opposed to one it merely accepts.

   A bump whose diff is additive and whose commit changes only the coordinates, fixtures and read-side schemas leaves the floor alone. Say which way it went in the commit message.

Note the asymmetry that is deliberate: the version gate REFUSES a codex below the floor and only WARNS on a newer one, because unknown fields are silently ignored and "newer" is overwhelmingly compatible. The conformance test, not a string compare, is what fails when the protocol actually moves.

## Then re-prove the log format — this is the step that gets skipped

A version gate proves Frizz is talking to the right binary. It says nothing about whether that binary still WRITES the transcript Frizz reads, and that is the failure this system has actually suffered. Codex 0.153 respelled its rollout: every semantic event moved onto one `event_msg/item_completed` envelope carrying a typed `item`, and the flat payloads Frizz read stopped being written. Nothing threw. The fold returned empty — no assistant text, no user turns, no sub-agents — while the turn brackets, which had not moved, kept working, so threads went in-flight and came to rest perfectly with nothing on the board.

[`log-format-conformance.test.ts`](../packages/server/src/backend/log-format-conformance.test.ts) is the detector. It finds the newest substantial session on this machine written by the PINNED build — both vendors stamp their own build into the transcript, Codex in `session_meta.payload.cli_version` and Claude on every record's `version` — folds it through the production path, and asserts the things that went to zero are not zero.

**It SKIPS when nothing on the machine was written by the new pin, which is the state every bump leaves behind.** A skip is not a pass; it means the format is unproven. So after bumping:

1. Write a real session on each backend you moved, without restarting the server: `claude-probe.mjs` for Claude, one `codex exec` on the pin for Codex. That turn has to run a shell command, because the gate fails a rollout with no `tool-call` ("Reply with ok" wrote one on 0.167.0), and it needs `</dev/null`, because `codex exec` under a worker's shell otherwise waits on stdin forever. A server restart sweeps the provisioned build away, so re-run `provision.mjs codex` if the binary has gone. The gate skips a transcript touched in the last ten minutes, so wait that long.
2. `nub run test packages/server/src/backend/log-format-conformance.test.ts` and confirm it reports `pass`, not `skipped`.

If it fails, the vendor moved the format and the parser — `parseCodexLine` in [`codex.ts`](../packages/server/src/backend/codex.ts), `applyRecord` in [`tailer.ts`](../packages/server/src/tailer.ts) — is what has to change. Capture a redacted rollout into `codex.fixtures/` alongside the existing ones as the regression pin, the way `multi-agent-0153.jsonl` records the last such move.

## Then the releaser ships it — a pin nobody can install is not a bump

The point of a pin is the binary a user runs. The selected `frizz-server` generation owns the provider pins; updating that server brings the new private runtimes without changing the stable launcher or global provider installations. A pin that lands on `main` alone remains unpublished, and publishing it is the dedicated releaser thread's job (maintainer 2026-10-11, superseding 2026-09-07's *"you should cut a new release as well"*; see `AGENTS.md` § Cutting a release). Any other thread asked to move a pin lands it on `main` and stops there: no package version, no dispatch, no offer to. The sequence below is the releaser's.

### Releases publish from the `release` branch, not from main

Main answers "has this landed?". [`release`](../.github/workflows/release.yml) answers "has this been VERIFIED and chosen to ship?" — and only the second one is ever released. Since 2026-09-23 neither branch publishes on its own: the workflow runs on `workflow_dispatch` alone, so `release` selects the commit and a maintainer's dispatch starts the run. The split exists because main moves under you: several agents land on it continuously, so the commit you verified and the commit that would publish are routinely not the same one, and a release from main carries whatever arrived in between (maintainer, 2026-09-08: *"you can bump these versions and do your own testing independent of whatever's landed on `main`"*).

**`release` is a fast-forward pointer into main, never a fork.** It holds no commits of its own. You pick the main commit you actually tested and move the branch to it, which keeps the published tree a real snapshot of main — nothing to cherry-pick, nothing to merge back — while leaving later, unverified commits behind. If it ever needs a non-fast-forward push, stop and look rather than forcing it.

### The sequence

1. **Cut the server version on main.** Raise `version` in [`packages/server-release/package.json`](../packages/server-release/package.json) and commit as `chore(release): frizz-server X.Y.Z`. Provider pins, frontend and server changes ship together there. Leave the root shell version alone unless its launcher changes; a new shell's `frizzServer.version` names its exact bootstrap server. Patch bumps remain the default.
2. **Look at what ships with you.** `git log release..HEAD` is the exact set. Anything there you have not verified either gets verified now or gets left behind by pointing `release` at an earlier commit — that choice is the whole reason the branch exists.
3. **Verify the commit you are about to publish, not "the tree".** `nub run test` and `nub run typecheck` against that sha. Typecheck is the release workflow's own gate, deliberately not the full suite. The `test` job in `ci.yml` runs the suite on a push to `main`, and the release does not wait for it.
4. **Push main, then fast-forward and push `release`.** `git push origin main`, then `git branch -f release <sha> && git push origin release`. This chooses the commit that will ship; it starts nothing.
5. **Dispatch the workflow.** `gh workflow run release.yml --ref release`. This is the only thing that starts a release, and the workflow refuses any ref but `release`. It also refuses a version that does not directly follow the highest one npm serves, so a release never overtakes one npm has not served; a number that was never published takes `-f allow_version_gap=true` (see `AGENTS.md` § Cutting a release).
6. **Ask for the approval, then wait until npm serves the version.** `npm stage publish` only queues a version: npm reviews it, and the registry serves it after a maintainer approves it with 2FA. Once the `stage` job is green, which ends the run, `stager ask 'frizz-server@<version>'` posts the notification, one authenticator code approves it, and `stager await 'frizz-server@<version>'` returns once npm serves it. A 404 in that window is the queue, not a failed release: never stage again (see `AGENTS.md` § Cutting a release).

The workflow stages every version npm does not have yet, `frizz-server` and `frizz` in the same run, and the approval orders them: its one code approves the server first and then the shell, because a shell fetches its pinned server from the registry on first boot. When a shell ships too, the ask names both (`stager ask 'frizz-server@<server version>' 'frizz@<shell version>'`). The run checks each version independently in npm. Every release, server-only ones included, gets a tag, a GitHub release and its release notes, which the releaser publishes after the run with `nub scripts/tag-release.mjs [frizz-server] --notes-file <file>`, at npm's recorded `gitHead` (`AGENTS.md` § Cutting a release, step 7). Re-dispatching is always safe: every version is checked against the registry first, so a published one is skipped.

**`pnpm install --frozen-lockfile` is the first gate the workflow hits, and it is the one that actually fails.** This repo's toolchain is `nub` but CI installs with pnpm, and the two disagree about how to record a specifier the root `pnpm.overrides` rewrites — nub writes what the manifest literally declares, pnpm writes what the override resolves to. That flipped `packages/web`'s react lines back and forth three times and broke a release each time, until the manifest was changed to declare the override's own version so both agree. If a release dies at the install step, check for that class first: reproduce it exactly with `git worktree add /tmp/check <sha>` and `pnpm install --frozen-lockfile` there, rather than trusting a local `nub install`.

**A version bump on main is inert.** Pushing main publishes nothing, and neither does moving `release` — only a dispatch does. On a runtime-watch wake, compare `packages/server-release/package.json` against `npm view frizz-server version`, and root `package.json` against `npm view frizz version`; checking only the shell misses an unpublished provider pin.
